# plan-contract v1 — 계획 문서의 기계 판독 블록

> `implementation-plan.md` §5 에 **명시 블록**을 추가해, 드리프트 탐지의 기준선(계약)을 기계가 읽게 한다.

---

## 1. 왜 산문을 파싱하지 않는가

기존 §5 실측(3건) 결과 형식 변산이 파싱 한계를 넘는다.

| 사례 | 형식 |
|---|---|
| A | 불릿 + 백틱 경로 |
| B | ASCII 트리 + 마크다운 표(라인 수 컬럼 포함) |
| C | ASCII 트리 + 볼드 백틱 불릿 |

결정적 문제는 **트리가 실재하지 않는 루트를 붙인다**는 것이다.

```
core-system/     Core-System/     [project_root]/
```

여기에 `(신규)`, `(수정: ... 추가)`, `# 패키지 마커` 같은 인라인 주석이 섞인다.
휴리스틱 파서는 오탐·미탐을 만들고, **드리프트 탐지기가 자기 입력에서 드리프트한다.**

→ 산문은 사람 몫으로 그대로 두고, 기계용 블록을 따로 둔다.
→ 기존 문서에 **소급 적용하지 않는다.** 블록이 없으면 계약 없음으로 처리한다.

---

## 2. 위치와 형태

`## 5. 주요 파일 변경 예상` 섹션의 **맨 끝**, 산문 뒤에 둔다.
사람이 먼저 읽고, 기계가 마지막을 읽는다.

~~~markdown
## 5. 주요 파일 변경 예상

### 신규 생성 파일
(기존 산문 그대로)

### 기존 파일 수정
(기존 산문 그대로)

### 작업 범위 (기계 판독)

```yaml contract
contract_version: 1
scope:
  allow:
    - core/shop/**
    - core/core/config/aws.py
  deny:
    - core/common/**
```
~~~

- fence info string 은 `yaml contract` 고정. 첫 단어가 `yaml` 이므로 GitHub 하이라이팅이 정상 동작하고,
  둘째 단어가 탐지 마커가 된다.
- 문서당 `yaml contract` 블록은 **최대 1개**. 2개 이상이면 파싱 오류로 처리하고 계약 없음으로 폴백한다.

## 3. 스키마 v1

```yaml
contract_version: 1        # 필수. 정수
scope:                     # 필수
  allow: [<pathspec>, ...]  # 필수, 1개 이상
  deny:  [<pathspec>, ...]  # 선택
```

**v1 은 이 두 필드가 전부다.** 근거 없는 정밀도는 노이즈이고, 노이즈는 이 체계를 죽인다.

### 신규/수정을 구분하지 않는 이유

술어가 묻는 것은 "이 경로를 건드려도 되는가" 하나뿐이다.
생성이냐 수정이냐는 판정을 바꾸지 않는다. 작성자에게 분류 부담만 준다.
→ `allow` 하나로 합친다. (산문 쪽 신규/수정 구분은 사람용으로 유지)

### 예약 키 (v1 미구현)

아래는 v2 이후 후보다. **v1 파서는 모르는 키를 무시한다** (전방 호환).

`forbid_patterns` · `phase_gates` · `watch` · `rejected`

## 4. 경로 규격

- **레포 루트 기준 상대 경로.** POSIX 구분자(`/`). 선행 `./` 나 `/` 금지
- **가짜 루트를 붙이지 않는다.** `Core-System/core/shop/...` (X) → `core/shop/...` (O)
  — 실측에서 가장 흔한 오류
- `*` = 한 세그먼트, `**` = 0개 이상 세그먼트
- 매칭 대상은 git 이 보고하는 경로 문자열
- 디렉터리를 의도하면 `**` 를 명시한다. `core/shop` 은 그 이름의 파일만 가리킨다

### 우선순위

**`deny` 가 `allow` 를 이긴다.** 넓게 열고 좁게 막는 조합을 쓸 수 있다.

```yaml
allow: [core/shop/**]
deny:  [core/shop/legacy/**]
```

### 암묵 allow

선언하지 않아도 항상 허용된다. 선언 부담과 오탐을 동시에 줄인다.

| 경로 | 이유 |
|---|---|
| `documents/tasks/<현재 브랜치>/**` | 계획 문서 자신. 작업 중 갱신되는 것이 정상 |
| `**/migrations/**` | 생성물이며 git 미추적 |

**테스트는 암묵 허용에 넣지 않는다.** 실측 3건 모두 테스트 파일을 §5 에 명시하고 있었고,
TDD 가 규칙이므로 "어느 테스트를 쓸 것인가" 는 계획이 답해야 할 질문이다.
암묵 허용으로 돌리면 그 질문이 사라진다.
→ 마찰이 실제로 문제가 되면 그때 실측 근거를 갖고 뒤집는다.

## 5. 세분도 지침

**확신하는 만큼만 좁힌다.**

| 상황 | 권장 |
|---|---|
| 건드릴 파일이 확정됨 | 파일 단위 — `core/shop/urls.py` |
| 앱은 알지만 파일은 유동적 | 앱 단위 — `core/shop/**` |
| 앱 경계를 모름 | **계획이 아직 덜 됐다는 신호.** 블록을 쓰지 말 것 |

파일 단위로 추측해서 적으면 정상 작업마다 escalation 이 터진다.
오탐이 잦으면 사람이 경보를 끄고, 그 순간 체계 전체가 죽는다.
**앱 단위로 시작해서 데이터를 보고 좁힌다.**

---

## 6. 계약 부재 시 동작

블록이 없거나, 파싱 실패거나, `allow` 가 비었으면 → **계약 없음**.

- Tier 0 의 계약 기반 술어(`allow`/`deny`)만 끈다. 계약 무관 술어(검증 무효 탐지 등)는 그대로 돈다
- escalation 레인을 끈다
- **작업을 차단하지 않는다** — 차단하면 계획 작성 회피 유인이 생긴다
- 세션당 1회 "무계약 작업 중" 만 알린다
