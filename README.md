# drift-detect

> 코딩 에이전트의 **지침 이탈(instruction escape)** 과 **컨텍스트 드리프트(context drift)** 를
> 외부에서 탐지하고, 그 판정을 세션의 hook 이 집행하는 감사 하네스.

에이전트가 스스로를 감사하지 않는다. 감사 여부를 에이전트가 결정하지도 않는다.

---

## 왜 만드는가

코드 생성 속도가 올라가면 계획·리뷰·테스트·배포가 병목이 된다
([The AI-Native SDLC Playbook](https://academy.claude.com/courses/ai-native-sdlc-playbook)).
그런데 실무에서 더 비싼 병목은 따로 있다 — **에이전트가 합의된 범위를 벗어났는지 아무도 실시간으로 모른다는 것.**

기존 대응의 한계:

| 대응 | 한계 |
|---|---|
| CLAUDE.md 에 규칙을 적는다 | 준수 여부가 에이전트의 기억과 선의에 의존 = **예상 기준** |
| 에이전트에게 자가점검을 시킨다 | 판정 주체가 드리프트 당사자 |
| 사후 코드 리뷰 | 이미 벌어진 뒤. 되돌리는 비용이 큼 |
| 매 도구 호출마다 LLM 감사 | 지연이 세션 wall-clock 에 직렬로 붙고, 단일 호출만 보이므로 궤적을 못 본다 |

---

## 설계 원칙

### 1. 예상을 기준으로 삼지 않는다

> 하네스에서 "예상"을 기준으로 삼으면 결과가 나쁘다.

- 「단일 파일 / 300줄 이하면 직접 수정 허용」 같은 **자기판정 예외**는 범위가 커져도 계속 직접 수정하는 드리프트의 원인이 된다.
- 「N턴마다 감사」도 예상이다 — 드리프트가 N턴 안에 일어난다는 예상.
- 선형 추정(projected)에는 **조언 권한만** 주고 게이트 권한을 주지 않는다.

→ 트리거는 **관측된 이벤트**여야 한다. 카운터도 추정도 아니다.

### 2. 판정 주체를 확률적인 것으로 되돌리지 않는다

술어로 표현 가능한 것은 전부 술어로 집행한다.
LLM 은 **술어로 판정이 불가능한 지점에만** 소집한다.

### 3. 오라클과 액추에이터를 분리한다

```
audit process  = 오라클 — 판정만 한다. 아무 권한이 없다.
     │ verdict 파일 write
     ▼
task session hook = 액추에이터 — 실제 차단은 여기서 일어난다.
```

감사관이 세션을 멈추는 것이 아니라, **감사관이 덫을 놓고 그 세션의 다음 hook 이 밟는다.**

- 감사관이 느려도 세션이 느려지지 않는다 (hook 은 LLM 을 기다리지 않는다)
- 감사관이 죽어도 세션이 죽지 않는다
- 감사 여부가 드리프트 당사자의 협조에 의존하지 않는다

### 4. 얕은 감사를 자주 하지 말고, 깊은 감사를 사건 발생 시에 한다

판정 품질은 빈도가 아니라 **판정당 관측 폭**에 비례한다.

## 아키텍처

### Tier 0 — predicate (매 도구 호출 / 동기 / 비용 0 / 지연 ~0)

```
Edit·Write 대상이 deny_paths ∈                  → BLOCK
forbid_patterns 매치                             → BLOCK
테스트 PASS 주장인데 실행 경로 플래그 없음        → BLOCK (검증 무효)
Edit 대상이 allow_paths ∉                       → PROMPT + escalation 마킹
watch / rejected 키워드 등장                     → FLAG
```

이것이 "직후 확인" 이다. LLM 없이 성립한다.

### Tier 1 — escalation (관측 이벤트 기반 / 비동기 / out-of-process)

| 관측 이벤트 | LLM 소집 | 판단 내용 |
|---|---|---|
| `allow_paths` 밖 Edit | O | **계획 이탈인가, 계획이 낡은 것인가** |
| sub-agent 완료 | O | 보고 내용 vs 실제 diff 대조 |
| 커밋 / PR 시도 | O | hand-off 게이트 (무맥락, 계약서 + diff 만 입력) |
| deny / forbid hit | X | 술어로 확정됨 |

턴 카운터 없음. **탐지는 공짜, 판정만 유료.**

### Tier 2 — hand-off 게이트 (별개 세션 / 무맥락)

입력은 둘뿐 — ① 계약서 ② diff. transcript 금지.
상관된 맹점(같은 지침을 읽은 같은 모델이 똑같이 드리프트하는 경우)이 우려되는 건에 한해 타 벤더 교차검증.

## 계약 (contract)

드리프트는 **무엇으로부터의** 이탈인가? 비교 대상이 데이터로 존재해야 한다.
계약서가 산문이면 준수 여부가 다시 에이전트의 기억에 의존한다 — 그게 정확히 "예상 기준".

### 기준선: `implementation-plan.md`

작업 시작 **이전**에 작성되고, **로컬 파일**이며, 경로가 브랜치에서 결정론적으로 도출되는 문서를 기준선으로 삼는다.

```
documents/tasks/$(git branch --show-current)/implementation-plan.md
```

이슈 트래커 본문을 기준선으로 삼지 않는다 — hook 이 매 호출마다 원격 API 를 칠 수 없고,
API 키 하나가 죽으면 계약 전체가 사라지는 단일 장애점이 된다.
트래커는 **사람의 SSOT** 로 두고, 로컬 계약은 거기서 **컴파일된 산출물**로 취급한다.

### 매핑

| implementation-plan 섹션 | contract 필드 | 위반 시 |
|---|---|---|
| §5 주요 파일 변경 예상 (신규 + 수정) | `allow_paths[]` | escalation |
| §1 변경 제약사항 › 변경 불가 / 호환성 유지 | `deny_paths[]`, `deny_patterns[]` | BLOCK |
| §2 제약 조건 (기술적) | `forbid_patterns[]` | BLOCK |
| §3 Phase 별 완료 기준 체크박스 | `phase_gates[]` | 상태 전이 판정 |
| §4 리스크 | `watch[]` | FLAG |
| (전역 메모리) 재제안 금지 항목 | `rejected[]` | FLAG |

세션 시작 시 1회 파싱 → `.claude/state/contract.json` 캐시. 매 호출 파싱 아님.

### `allow_paths` 밖 Edit 이 설계의 중심

§5 는 "변경 **예상**" 이므로 계획 자체가 틀릴 수 있다. 그래서 BLOCK 이 아니라 escalation 이고,
판정 결과가 둘로 갈린다:

- **이탈** → 되돌리고 계약 유지
- **계획이 낡음** → plan §5 갱신 → 계약 재컴파일

탐지는 술어로 공짜, 판정은 술어로 불가능 — escalation 의 교과서적 지점.

### 계약이 없을 때

**차단하지 않는다.** 차단하면 계획 작성 회피 유인이 생긴다.
무계약이면 기존 술어만 돌고 escalation 레인은 끈다. 세션당 1회 "무계약 작업 중" 만 알린다.

## verdict

판정은 서술이 아니라 **hook 이 실행할 수 있는 명령**이어야 한다. "드리프트 의심됨" 은 쓸모없다.

```json
{
  "verdict": "deviation | plan_stale | clean",
  "action":  "deny_path | ask | require_plan_update | proceed",
  "target":  "<파일 경로 + 위반한 계약 조항>",
  "reason":  "<1줄. 모델에게 전달되는 유일한 서술>",
  "ttl_tool_calls": 8
}
```

- `action` = 액추에이터가 읽는 필드
- `reason` = 모델에게 돌려주는 필드
- `ttl` 이 있어야 교정 후 덫이 남지 않는다

### 앵커링 — 턴이 아니라 경로에

비동기이므로 판정이 돌아올 때 세션은 이미 이동해 있다.
**턴 번호에 앵커링하면 경쟁 조건에 진다.** `target` 을 파일 경로 + 계약 조항에 앵커링하면
몇 턴이 지나도 판정이 유효하고, 모델이 그 파일을 건드리는 순간 정확히 발동한다.

---

## 액추에이터 사다리

| 강도 | 메커니즘 | 효과 | 사람 개입 |
|---|---|---|---|
| 0 | PostToolUse `additionalContext` | 모델이 읽음, 행동은 자유 | 없음 |
| 1 | UserPromptSubmit 주입 | 다음 턴 시작에 상기 | 없음 |
| 2 | PreToolUse `permissionDecision: ask` | 승인 프롬프트 | **있음** |
| 3 | PreToolUse `deny` + reason | 호출 거부 + **사유를 모델에 전달** | 없음 |
| 4 | Stop hook block | 미교정 시 종료를 막음 | 없음 |

**강도 3이 핵심.** 단순 차단이 아니라 사유를 되돌려주는 차단이라 모델이 같은 턴에 자가교정한다.
인터럽트이면서 동시에 교정 신호다.

### 판정을 누가 받는가

| verdict | 수신자 | 강도 |
|---|---|---|
| `deviation` (확신) | 모델 | 3 — 자가교정, 사람 안 깨움 |
| `plan_stale` | 모델 | 1 + 커밋 시점 4 (plan 갱신 전 hand-off 차단) |
| 모호 / 계약 자체의 변경 | **사람** | 2 |

전부 사람에게 보내면 인간 속도 병목을 재생산한다.
전부 모델에게 보내면 모델이 감사관과 협상하기 시작한다 (Goodhart).
→ **정답이 유일하지 않은 건만 사람에게.**

## 실행 형태

```
PostToolUse  → 술어 검사 (동기, 마이크로초)
             → 의심 시 verdict 요청 write + 백그라운드 감사 프로세스 기동 (논블로킹)

PreToolUse   → verdicts/*.json 읽기 (파일 I/O)
             → target 매치 시 action 집행 (deny / ask)

Stop         → 미해소 verdict 있으면 block
```

**hook 은 LLM 을 기다리지 않는다.** 요청만 던지고 즉시 반환, 판정은 다음 호출에서 수거.

### 왜 sub-agent 가 아니라 외부 프로세스인가

sub-agent 로 감사를 부르면 컨텍스트는 분리되지만 **호출 여부를 host 가 결정한다.**
드리프트 중인 당사자가 자기 감사 시점을 정하는 구조다.
hook 이 별도 프로세스를 띄우면 감사가 에이전트의 협조에 의존하지 않는다.

"외부" 의 실질적 의미는 **벤더가 아니라 통제권**이다.

---

## 오염 방지

판정문이 컨텍스트에 쌓이면 감사 체계 자체가 오염원이 된다.

- 발화될 때만 주입. "이상 없음" 은 주입하지 않는다
- 주입은 극도로 짧게
- 전체 판정 로그는 컨텍스트가 아니라 **파일**로 남기고 사후 검증에만 쓴다

## 루프 연동 (선택)

이슈 트래커의 워크플로 상태가 그대로 FSM 이 된다.

```
작업 중 ──[Tier0 clean + phase_gates 충족 + CI green]──▶ 코드리뷰 중
   ▲                                                        │
   └──────────[리뷰 FAIL 또는 escalation 이탈 판정]──────────┘
```

**구동 주체는 상태기계(코드)여야 한다.** LLM 오케스트레이터를 두면 드리프트할 수 있는 주체가 하나 더 늘고,
감사관의 감사관이 필요해진다.

### 선결 조건

루프는 자기 게이트보다 신뢰할 수 없다.
상태 전이 근거가 에이전트의 자기보고이면, 자동화한 것은 신뢰가 아니라 **신뢰의 부재를 반복하는 속도**다.
→ CI 가 뱉는 exit code 가 있어야 상태기계가 읽을 것이 생긴다.

## 비용

| 항목 | 비용 |
|---|---|
| Tier 0 | 0 |
| escalation | 50~100회/일 × 20k cold ≈ 1~2M 토큰/일 |
| 실질 증가 | **+1~3%** |

비교: 매 도구 호출 감사는 3,000회/일 규모이며, 유효한 컨텍스트(20k+)를 주면 실질 +40~50%.
게다가 감사 호출은 전부 cold input 이라 cache_read 가 지배하는 본 세션과 단가가 10배 다르다.

**얕으면 싸지만 무용하고, 쓸모 있으면 싸지 않다** — 이것이 per-call 감사의 함정.

## 기각된 설계

재제안 금지. 기각 사유를 남겨 같은 논의를 반복하지 않는다.

| 설계 | 기각 사유 |
|---|---|
| PostToolUse 매 호출 LLM 감사 | ① 단일 호출 payload 로는 궤적이 안 보임(관측 문제, 예산으로 해결 불가) ② 동기 실행이라 하루 100~200분이 세션 wall-clock 에 직렬로 붙음 ③ 판정 주체를 확률적인 것으로 되돌림 |
| N턴마다 주기 감사 | N 자체가 예상. 드리프트가 N턴 안에 일어난다는 가정 |
| 감사 sub-agent (Agent tool) | 호출 여부를 드리프트 당사자가 결정 |
| LLM 오케스트레이터로 루프 구동 | 드리프트 주체 증가. 감사관의 감사관 문제 |
| 이슈 트래커 본문을 계약 기준선으로 | hook 이 매 호출 원격 API 호출 불가. API 키 단일 장애점 |
| 계약 없는 작업 차단 | 계획 작성 회피 유인 |
| 타 벤더 LLM 을 Tier 1 에 상시 투입 | 비용만 증가. 상관된 맹점이 문제인 Tier 2 에서만 유효 |

## 상태

**설계 단계.** 구현 착수 전.

### 착수 순서

1. `implementation-plan.md` §5 에 기계가 읽는 블록 규격 고정 (사람용 서술은 유지)
2. 계약 컴파일러 (plan → `contract.json`)
3. Tier 0 술어 집합
4. verdict 스키마 + 액추에이터 hook
5. escalation 감사 프로세스
6. (선택) FSM 루프 연동

### 미결

- §5 파싱 규격 — 현재 트리 다이어그램 + 불릿 혼용이라 파싱 불안정
- 기존 계획 문서의 소급 적용 범위 (신규만 적용이 안전)
- `deviation` / `plan_stale` 판정의 신뢰도 임계 — 어느 선부터 사람에게 올릴 것인가
